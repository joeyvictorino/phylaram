## 1. Executive Summary

PhylaRAM is an open-source, non-invasive Windows physical memory acquisition tool engineered specifically for digital forensics and incident response (DFIR). It captures physical RAM without intermediate translation layers, compression distortion, or memory virtualization side-effects.

This document details the core invariants, memory topology contracts, sparse raw imaging model, and cryptographic provenance guarantees enforced by PhylaRAM.

---

## 2. Fundamental Invariants

### Invariant 1: Flat Physical Address Mapping
In a flat RAW image generated by PhylaRAM:
$$\text{File Offset} = \text{Physical Address}$$

Unlike container formats (such as raw crash dump `.dmp` or compressed `.aff4` archives) which require external parsers, a flat RAW image allows direct hex inspection, raw string searches (`strings -o`), YARA rule scanning, and direct memory analysis in Volatility 3 and MemProcFS without header decompression.

### Invariant 2: Hardware & MMIO Hole Preservation
Physical RAM is rarely contiguous. Modern x64 platforms contain hardware-reserved ranges, PCIe memory-mapped I/O (MMIO) regions, ACPI reclaim regions, and Resizable BAR (ReBAR) apertures.

PhylaRAM preserves these unmapped physical address ranges as **sparse file holes** (`FSCTL_SET_SPARSE` on NTFS/ReFS) or zero-byte runs (on flat stdout streams):
- Unmapped holes consume **zero physical disk clusters**.
- Logical reads across holes transparently return `0x00` bytes.
- The logical size of the output file always matches `HighestPhysicalEnd`.

### Invariant 3: Cryptographic Zero-Gap Hashing
When calculating the SHA-256 hash of the memory image:
1. Acquired physical RAM bytes are fed into the cryptographic stream at their exact physical offset.
2. Any unmapped physical hole or unreadable page is hashed as `0x00` zero bytes up to `HighestPhysicalEnd`.
3. The resulting SHA-256 hash matches the output of standard forensic disk hashing utilities (`hashdeep`, `sha256sum`, `fciv`) executed against the flat RAW image on disk.

## 3. Kernel Mode Acquisition Architecture

### 3.1 DDI Contract: `MmCopyMemory`
PhylaRAM uses the Windows Memory Manager's official kernel DDI:
```c
NTSTATUS MmCopyMemory(
    _Out_ PVOID TargetAddress,
    _In_  MM_COPY_ADDRESS SourceAddress,
    _In_  SIZE_T NumberOfBytes,
    _In_  ULONG Flags, // MM_COPY_MEMORY_PHYSICAL
    _Out_ PSIZE_T NumberOfBytesTransferred
);
```

#### Why `MmCopyMemory(MM_COPY_MEMORY_PHYSICAL)` is Superior:
- **No Page Table Corruption:** Does not modify PTEs or alter virtual memory page tables.
- **No Virtual Memory Mapping Limit:** Unlike `MmMapIoSpace`, it does not consume system PTEs or pool exhaustion in the kernel virtual address space.
- **Hardware Failure Isolation:** If a physical page fails to read (e.g. bad ECC page, uncorrectable hardware fault), `MmCopyMemory` returns `STATUS_DEVICE_DATA_ERROR` without bugchecking (BSOD) the target host.

### 3.2 Live Ring 0 Kernel Hints
During driver initialization, PhylaRAM queries critical kernel pointers to eliminate brute-force symbol scanning during offline analysis:
1. **System Process Directory Table Base (CR3):** Acquired via brief `KeStackAttachProcess(PsInitialSystemProcess, &apcState)` at `PASSIVE_LEVEL`. Provides Volatility 3 and MemProcFS with the exact page table root needed to initialize page translation instantly.
2. **Kernel Base & Size:** Extracted from NTOSKRNL PE headers via `RtlPcToFileHeader`.
3. **Executing KPCR:** Read from `%gs:[0x18]`.
4. **Hypervisor Presence:** Checked via CPUID `01H:ECX[31]`.

## 4. Fault Isolation & Unreadable Page Recovery

When physical memory acquisition encounters unreadable or guarded hardware pages, PhylaRAM applies a two-tier acquisition strategy:

```
[16 MiB Fast Path (PHYLA_MAX_TRANSFER)]
               │
               ▼
   Did MmCopyMemory copy all bytes?
         ├── Yes ──► Continue 16 MiB chunking
         │
         └── No  ──► Isolate Unreadable Span at 4 KiB Granularity
                           │
                           ├── Read 4 KiB page
                           ├── If read succeeds ──► Write to RAW & update SHA-256
                           └── If read fails    ──► Record NTSTATUS in map.json & pad zero
```

Every unreadable extent is recorded in `memory.raw.map.json` with its exact starting physical address, length, and NTSTATUS error code.

## 5. Offline Cryptographic Verification

The standalone Rust offline verification utility (`phylaram-verify`) validates three mathematical properties before evidence is admitted to court:

1. **Monotonic Disjoint Ordering:**
   $$\forall i < j: \quad \text{Range}[i].\text{start} + \text{Range}[i].\text{length} \le \text{Range}[j].\text{start}$$
2. **Byte Accounting Balance:**
   $$\text{Acquired Bytes} + \text{Unreadable Bytes} = \text{Physical RAM Bytes}$$
3. **SHA-256 Digest Match:**
   $$\text{SHA256}(\text{Logical Raw File}) == \text{map.json}[\text{"sha256"}] == \text{memory.raw.sha256}$$
